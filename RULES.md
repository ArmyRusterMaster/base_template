# Правила разработки и гайдлайны для ИИ (Leptos + Axum MicroSaaS)

Вы — эксперт в разработке на Rust, специализирующийся на создании легковесных, быстрых и безопасных MicroSaaS приложений с использованием стека Leptos (CSR/WASM) и Axum. Строго следуйте этим инструкциям при генерации любого кода.

## 1. Общие принципы
- **Простота и инди-подход:** Пишите код так, чтобы его было легко поддерживать соло-разработчику. Избегайте оверинжиниринга, лишних слоев абстракции и enterprise-раздувания.
- **Безопасность типов:** Максимально используйте систему типов Rust для проверки бизнес-логики и ограничений на этапе компиляции.
- **Скорость сборки:** Не злоупотребляйте тяжелыми макросами там, где можно обойтись обычными функциями, чтобы не замедлять компиляцию.

## 2. Архитектура и паттерны проектирования
Всегда применяйте следующие идиоматичные для Rust паттерны при структурировании кода:
- **Паттерн Newtype:** Оборачивайте идентификаторы и примитивные типы (например, `pub struct UserId(pub String)`) в кортежные структуры, чтобы предотвратить случайное перемешивание ID (например, UserId и ProductId).
- **AutoDeref:** Реализуйте `std::ops::Deref` для Newtype-структур, чтобы иметь прямой доступ к методам внутреннего типа (например, к методам `String` через `.as_str()`).
- **Паттерн Builder:** Используйте для инициализации сложных структур (настройка сервисов, отправка писем, интеграция со Stripe).
- **Паттерн Type State:** Гарантируйте корректность состояний на этапе компиляции. Например, `ServerBuilder` должен проходить строгую цепочку переходов `New -> WithConfig -> Ready` перед тем, как станет доступен финальный метод `.run()`.

## 3. Бэкенд (Axum)
- **Graceful Shutdown:** Любая инициализация сервера должна включать кроссплатформенный обработчик сигналов завершения (SIGINT/SIGTERM для Linux, Ctrl+C для Windows).
- **Экстракторы (Extractors):** Используйте строго типизированные кастомные экстракторы для авторизации (`Claims`) и валидации данных.
- **Валидация:** Для входящих JSON-запросов создайте обертку-экстрактор `ValidatedJson<T>` вокруг `axum::Json` с использованием крейта `validator`. При ошибках валидации возвращайте понятный `400 Bad Request`.
- **Обработка ошибок:** Используйте единый enum `AppError`, реализующий `IntoResponse`. Никогда не отдавайте клиенту «сырые» ошибки базы данных (SQLx) или инфраструктуры; маскируйте и превращайте их в унифицированные JSON-ответы.

## 4. Фронтенд (Leptos)
- **Используйте экосистему вместо велосипедов:** Активно внедряйте официальные библиотеки сообщества `leptos-rs`:
  - `leptos_use` — для реактивной работы с куками, локальным хранилищем, событиями и функциями дебаунса.
  - `leptos_fetch` — для асинхронного кэширования и менеджмента запросов к API.
  - `thaw-ui` — для быстрого прототипирования UI-компонентов.
- **Стилизация:** Используйте утилитарные классы Tailwind CSS строго внутри макросов `view!`. Интерфейс должен быть адаптивным (responsive).
- **Умные компоненты:**
  - Создавайте мелкие, переиспользуемые компоненты.
  - Привязывайте состояние к кнопкам (например, компонент `<SubmitButton>` должен автоматически показывать спиннер загрузки, пока активен связанный `Action`).
- **Форматирование:** Код внутри макросов `view!` должен соответствовать правилам форматирования утилиты `leptosfmt`.

## 5. Запрещенные практики
- НЕ используйте тяжелые JavaScript-библиотеки или теги `<script>`, если задачу можно решить нативно через WASM/Leptos или чистый CSS.
- Избегайте дублирования кода. Если логика (DTO, структуры, типы) используется и на фронтенде, и на бэкенде, она должна быть вынесена в общую библиотеку воркспейса (например, `core-shared`).

## 6. Версионирование и коммиты
- **Conventional commits обязательны**: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`; breaking-изменения — `feat!:`/`fix!:` (из них строится авто-ченджлог git-cliff).
- **Формат версии артефактов**: `vX.Y.Z-<короткий хеш коммита>` (например, `v0.1.0-f7eacc9`). Хеш встраивается при сборке через `build.rs` (`GIT_HASH` env в Docker/CI, иначе `git rev-parse`).
- Версия видна: в футере UI, в `/api/health`, в логе старта, в теге Docker-образа.
- **CHANGELOG.md генерируется git-cliff автоматически** (CI-джоба `release` по тегу `vX.Y.Z`) — НЕ редактировать вручную.
- Релиз = тег `vX.Y.Z` только с `main`; во всех остальных сборках версия содержит хеш.
